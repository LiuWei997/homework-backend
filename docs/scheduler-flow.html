Scheduler 執行流程

MySQL 保存任務狀態。Scheduler 取到期任務、發布至 RocketMQ，並在程序重啟後回收過期 lease。

核心：首次發布每批最多 50 筆；重試逐筆處理。MQ 發布不是和 MySQL 同一筆交易，可能重複投遞；最多三次逐筆重試，耗盡後進入 FAILED。

1. Scheduler 主循環

Spring 啟動排程執行緒DynamicScheduler.start() → runLoop()
↓
先記下喚醒版本，再取得現在時間SchedulerWakeup.generation()；本輪固定 cutoff
↓
回收過期 leaseTaskRecoveryService.recoverExpiredLeases(now)
PROCESSING → PENDING；PUBLISHING → PUBLISH_RETRY_WAIT 或 FAILED
↓
首次發布：批次直到沒有到期任務drainPending()
每批最多 scheduler.batch-size（預設 50）
重試：逐筆直到沒有到期任務drainRetries()
每次 claim / send 1 筆
↓
查下一個喚醒時間TaskRepository.findNextWakeAt()
取 PENDING 的 run_timestamp、重試的 next_attempt_at、PROCESSING / PUBLISHING 的 lease_until 最小值
↓
等待通知或逾時SchedulerWakeup.awaitChange(generation, wait)
等待最早到期時間，最多 scheduler.max-sleep（預設 30 秒）；醒來後回到本輪開頭

若一輪發生 RuntimeException，scheduler 記錄錯誤後等 1 秒或等通知，再重試整輪。停止時會 signal 等待中的執行緒。

2. 首次發布一批任務

① Claim 到期任務TaskDispatchService.dispatchPendingBatch() 呼叫 JdbcTaskRepository.claimDuePendingBatch()。短 transaction 內以 SELECT ... FOR UPDATE SKIP LOCKED 取最多 50 筆，再批次更新為 PROCESSING 並設定共用 lease token / expiry；transaction commit 後才繼續。
WHERE status = 'PENDING' AND run_timestamp <= :cutoff
ORDER BY run_timestamp, id
LIMIT :batchSize
FOR UPDATE SKIP LOCKED
② 跨過發布邊界beginInitialPublishBatch() 批次 CAS PROCESSING → PUBLISHING，增加 publish_attempts 並刷新 lease。任務進入 PUBLISHING 後不可再由 API 修改或取消。
③ 發送事件TaskDispatchService.publishBatch() 建立穩定 eventId = taskId:scheduleVersion。RocketMqTaskMessagePublisher.publishBatch() 序列化整批、按訊息大小拆分，再同步呼叫 RocketMQ；此時沒有 MySQL row lock。
④ 依發布結果更新狀態全部 send 成功後，markTriggeredBatch() 以 ID、狀態、token 和 lease 條件批次設為 TRIGGERED。若任一子批發送失敗或結果不明，整個 scheduler batch 會批次進入重試等待或 FAILED；已被 Broker 收下的訊息可能重送。
PENDING→PROCESSING→PUBLISHING→TRIGGERED

成功、失敗或 claim 狀態改變後，程式會嘗試批次失效 Redis detail cache。Redis 只負責快取，不參與排程判斷。

3. 發布失敗與程序恢復

發布失敗／結果不明狀態進入 PUBLISH_RETRY_WAIT 時設定下一次時間，並清除 lease。到期後 claimDueRetryBatch() 一次只 claim 1 筆，進入 PUBLISHING 再發送。
Lease 到期後回收PROCESSING 批次回到 PENDING；PUBLISHING 批次依重試預算進入等待或 FAILED。Broker 可能已收件，所以恢復後可能重送同一個 eventId。
重試策略（含 lease 到期回收）首次發布失敗後等 2 秒；第 1、2 次逐筆重試失敗後分別等 4、8 秒；第 3 次逐筆重試仍失敗就設為 FAILED。退避公式上限為 16 秒；以目前三次重試上限不會等到第 4 段。
PUBLISHING→ 失敗／lease 到期PUBLISH_RETRY_WAIT→ 到期重試PUBLISHING→ 耗盡FAILED

發送成功但 ACK 遺失，或 ACK 後 DB 更新失敗，都可能造成重複訊息。穩定 eventId 供 consumer 冪等去重；有限重試代表任務也可能以 FAILED 結束而未送達。

4. 喚醒來源

任務 API 變更TaskService.create/update/cancel() 發出事件；transaction commit 後 TaskCacheInvalidationListener.onScheduleChanged() 呼叫 SchedulerWakeup.signal()。
手動喚醒POST /scheduler/wakeup → SchedulerController.wakeup() → SchedulerWakeup.signal() → HTTP 204。

signal() 增加 generation 並通知 Condition。Scheduler 在等待前比對先前記錄的 generation；若查 DB 期間收到通知，generation 會改變，Scheduler 略過睡眠並重查，避免漏掉通知。直接 SQL 寫入或其他 app instance 的通知不會喚醒此 JVM，最多由 30 秒輪詢上限發現。

程式碼對照：DynamicScheduler、SchedulerWakeup、TaskDispatchService、TaskRecoveryService、JdbcTaskRepository、RocketMqTaskMessagePublisher、TaskCacheInvalidationListener、SchedulerController。
